**Parallel model:** OpenMP (shared-memory, single multi-core node)

## Problem
Apply convolution filters (Gaussian blur, box blur, sharpen, Laplacian and Sobel edge detection, emboss) to very large
images. Each output pixel is a weighted sum over a k x k neighbourhood of the input, so the cost is O(W x H x C x k^2).

## Why the problem size is "large"
A 6000 x 6000 RGB image has 36 MP (108 MB). With a 9 x 9 kernel, that is 36M x 3 x 81 ~ 8.7 billion multiply-adds
per pass - several seconds sequentially. Sizes are scaled up (e.g. 4000, 6000, 8000, 10000 px) and kernel size varied
(3, 9, 15) so the sequential version is clearly slow and speedup is measurable.

## Why it parallelizes well
Every output pixel depends only on the (read-only) input image, so there are no data dependencies between pixels:
an embarrassingly parallel, data-parallel loop nest with a high compute-to-memory ratio.

## Implementation plan
1. C++17 engine: PPM/PGM I/O, kernel library, sequential baseline, border handling (clamp-to-edge).
2. Parallel strategies: (a) `#pragma omp parallel for schedule(static)` over rows; (b) `collapse(2)` over 2D tiles with
   `schedule(dynamic)` for cache locality. Compare against sequential.
3. Correctness check: parallel output must be byte-identical to sequential output (`--verify`).
4. Benchmarking: vary image size, kernel size, thread count (1..N); record execution time, speedup S = T1/Tp and
   efficiency E = S/p; graphs generated by `benchmark/run_benchmark.py`.
5. Frontend: Flask web UI to upload an image, choose filter/threads, view before/after, timing and live scalability charts.
6. Report: analysis of speedup limits (memory bandwidth, Amdahl serial I/O portion, scheduling overhead, false sharing).
